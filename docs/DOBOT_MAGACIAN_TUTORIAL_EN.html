Chapter 2: ROS 2 Fundamentals from Scratch

2.1 What is ROS 2?

ROS 2 (Robot Operating System 2) is not an OS like Windows or Ubuntu; it is a distributed robotics software middleware. Built on the industrial DDS (Data Distribution Service) standard, ROS 2 enables separate programs (processes) to exchange data, synchronize clocks, and coordinate complex robotic tasks across multiple threads, processes, and network nodes seamlessly.

2.2 Core ROS 2 Primitives

1. Nodes (`rclpy.node.Node`)

A Node is an independent executable process responsible for a single task:

  • detection_node: Captures webcam frames, segments cubes, and publishes detected metric coordinates.
  • dobot_controller: Communicates over serial with the Dobot arm, manages safety limits, and executes trajectories.
  • dobot_ui_node: Renders the GUI interface and transmits operator commands.

2. Topics & Publisher-Subscriber Pattern

Topics provide unidirectional, asynchronous streaming data channels. A Publisher broadcasts messages without knowing who is listening, and Subscribers trigger callback functions whenever a new message arrives.

Topic Name Message Type Publisher Subscriber Description
/detected_objects std_msgs/msg/String (JSON) detection_node Dobot_UI, dobot_controller Real-time metric coordinates (X, Y, Z), colors, and cell assignments.
/detected_objects_image/compressed sensor_msgs/msg/CompressedImage detection_node Dobot_UI Low-latency compressed JPEG stream rendered in the GUI viewer.
/dobot_status std_msgs/msg/String (JSON) dobot_controller Dobot_UI State telemetry: X, Y, Z, R Cartesian pose, suction status, connection state.
/dobot_ui_cmd std_msgs/msg/String (JSON) Dobot_UI dobot_controller Control messages: mission dispatch, manual jog, homing, emergency stop.

Chapter 3: Computer Vision Pipeline with OpenCV

3.1 Camera Capture & V4L2 Video Streaming

On Linux, USB webcams interface via the Video4Linux2 (cv2.CAP_V4L2) kernel driver. Using hardware MJPG decoding enables low-latency streaming at 640 x 480 resolution and 30 FPS without taxing the CPU: 

import cv2

cap = cv2.VideoCapture('/dev/video0', cv2.CAP_V4L2)
cap.set(cv2.CAP_PROP_FOURCC, cv2.VideoWriter_fourcc(*'MJPG'))
cap.set(cv2.CAP_PROP_FRAME_WIDTH, 640)
cap.set(cv2.CAP_PROP_FRAME_HEIGHT, 480)
ret, frame = cap.read() # Output is a BGR NumPy array

3.2 Why HSV is Superior to RGB/BGR for Color Segmentation

Standard cameras output images in BGR (Blue, Green, Red). In BGR, illumination changes (shadows, daylight shifts, overhead flickering) simultaneously alter all three color channels, making thresholding unstable.

In contrast, HSV (Hue, Saturation, Value) isolates chromaticity from illumination:

  • H (Hue [0..180]): Encodes the pure spectral color independent of light intensity (e.g. Green is always ~35..85 regardless of room lighting).
  • S (Saturation [0..255]): Quantifies color purity, distinguishing vivid cube colors from white paper and highlights.
  • V (Value [0..255]): Quantifies luminance, allowing dark shadows to be filtered out cleanly.

3.3 Color Masking & Morphological Noise Filtering

We apply cv2.inRange() to produce binary masks, followed by morphological opening to eliminate salt-and-pepper noise: 

# Convert BGR to HSV
hsv = cv2.cvtColor(frame, cv2.COLOR_BGR2HSV)

# Define HSV boundaries for Green
lower_green = np.array([35, 80, 70])
upper_green = np.array([85, 255, 255])
mask = cv2.inRange(hsv, lower_green, upper_green)

# Morphological opening (Erosion followed by Dilation) removes noise
kernel = cv2.getStructuringElement(cv2.MORPH_RECT, (3, 3))
mask_clean = cv2.morphologyEx(mask, cv2.MORPH_OPEN, kernel)

3.4 Metric Perspective Homography

Because the overhead camera views the table at an oblique angle, perspective keystoning distorts distances. We compute a 3x3 Homography transform matrix:

  1. Detect the 4 outer corner coordinates of the grid in image pixel space (u, v).
  2. Define target metric dimensions: a square 114.5 x 114.5 mm planar grid.
  3. Calculate the matrix: cv2.getPerspectiveTransform(src_pts, dst_pts).
  4. Multiply any detected pixel centroid (u, v) by this homography matrix to obtain table-space millimeters (gx, gy), and map directly into Dobot robot base coordinates (rx, ry, rz)!

Chapter 4: Dobot Magician Control with pydobot2

4.1 Serial UART Protocol

The Dobot Magician communicates via a USB-to-UART serial interface at 115200 bps. The protocol transmits structured binary packets: Header (0xAA 0xAA) | Length | Command ID | Payload | Checksum. The pydobot2 library encapsulates this protocol into thread-safe Python methods.

4.2 Cartesian Workspace Limits

📐 Dobot Magician Working Envelope
  • X (mm): Forward/backward extension. Safe limits: 100.0 mm to 330.0 mm.
  • Y (mm): Lateral left/right rotation. Limits: -250.0 mm to +250.0 mm.
  • Z (mm): Vertical elevation. Limits: -60.0 mm to +160.0 mm.
  • R (deg): End-effector wrist orientation. Limits: -180.0° to +180.0°.

4.3 PTP Motion Modes: MOVJ vs MOVL

  • MOVJ_XYZ (Joint Movement): All joints interpolate simultaneously. The arm swings in a smooth, high-speed arc. Used for open transit between field waypoints.
  • MOVL_XYZ (Linear Movement): The end-effector moves strictly along a Cartesian straight line. Crucial for picking up cubes vertically (downward 90°) and rising clear of neighbors without lateral collisions.
from pydobot import Dobot
from pydobot.dobot import MODE_PTP

device = Dobot(port='/dev/ttyUSB0')
device.speed(velocity=150.0, acceleration=150.0)

# Move above cube at hover height (Joint interpolation)
device.move_to(200.0, 0.0, 80.0, 0.0, mode=MODE_PTP.MOVJ_XYZ)

# Descend straight down to pick cube (Linear interpolation)
device.suck(True)
device.move_to(200.0, 0.0, 12.5, 0.0, mode=MODE_PTP.MOVL_XYZ)

Chapter 5: GUI Architecture with PyQt

5.1 Event Loop & Thread Decoupling

PyQt runs an internal Event Loop that processes user inputs and repaints the screen. Running ROS 2 subscription loops (rclpy.spin()) on this main thread would cause the UI to freeze and stop responding.

The Solution: We isolate ROS 2 communication into a dedicated background worker thread, RosBridge(QThread):

  1. Main UI Thread: Listens for mouse clicks, manages layouts, and renders Qt widgets.
  2. Worker Thread (`RosBridge`): Continuously calls rclpy.spin_once() in the background. Incoming image frames and status JSONs are emitted across threads via thread-safe `pyqtSignal` instances, keeping the GUI 100% responsive.

Chapter 6: 3-Phase Mission Execution & Collision Avoidance

6.1 3-Phase Automated Mission Workflow

📋 3-Phase Mission Architecture
  1. Phase 1 (Clear Obstacles): Non-goal cubes located in the grid are picked and cleared to Feeder Slots 1..4 on the left.
  2. Phase 2 (Stack Goal): Target cubes are picked in sequence (#1..#4) and vertically stacked at Center Goal [1, 1] up to a strict 4-block limit (Z = 30.0, 55.0, 80.0, 105.0 mm).
  3. Phase 3 (Restore Obstacles): Once goal stacking finishes, all obstacle cubes in the feeders are returned to their original grid slots.

6.2 Goal Collision Avoidance System

When 4 cubes are stacked at Goal [1, 1], the tower reaches 130 mm tall. A straight-line trajectory between a feeder (Y = +79 mm) and a right-column cell (Y = -35 mm) would slice directly through the center goal, toppling the tower.

Intelligent Detour & Clearance Trajectory:

  • A cylindrical Keepout Zone (R = 38.0 mm) is established around Goal (176.0, 0.0).
  • _point_to_segment_dist() evaluates candidate straight trajectories against this keepout cylinder.
  • If a collision is detected, _plan_safe_transit() inserts a perimeter corridor detour waypoint:
    • North Corridor Bypass: Detours around the top perimeter via X = 222.0 mm.
    • South Corridor Bypass: Detours around the bottom perimeter via X = 132.0 mm.
  • Elevated Vertical Clearance: Whenever cubes exist on the goal, transit elevation is automatically increased to Z_transit = max(hover_z, 142.0 mm), safely clearing the 130 mm tower.
